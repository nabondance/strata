# Interpret a Strata report

Read the user's Strata JSON report and check `schemaVersion` before interpreting fields. This skill describes schema version 19; if the report has another version, inspect its fields and avoid assuming this schema still applies. Version 18 and earlier have no `lineAge`. Version 17 and earlier have no `mcp` server lists. Version 16 and earlier have no `upFront` labels. Version 15 and earlier do not resolve Claude `@path` imports, so they have no `imports` or `imported` components; version 14 and earlier have no `copilot` provider; version 13 and earlier have no `cursor` provider. Version 12 and earlier have no skill `listing` or `skillListingTokens`; version 11 and earlier have no `submodules`. Versions 8 and earlier repeated a full `components` list inside every revision; version 9 labeled `.agents/skills` files `codex` instead of `shared`.

Use `revisions` in array order as the first-parent history sampled by the report. Each revision has a commit `id`, `date`, `firstParent`, `componentCount`, `categoryTotals`, `estimatedTokens`, and `changes` from its predecessor. The first revision's changes are relative to an empty baseline. These totals are enough to describe growth over time without rebuilding any file list. If `shallow` is true, earlier history is unavailable. If `submodules` is present, its entries are Git submodules whose files were not analyzed. An entry with `configFiles` above zero holds that many recognized agent-configuration files, absent from every total, so do not describe the report as the repository's complete agent configuration; `null` means the submodule could not be checked. A merge appears as one revision measured against its first parent, not as a full branch history.

A revision does not list its files. The top-level `components` array holds every distinct file version in the history once (a path together with the blob stored there), ordered by path, so one path can appear several times with different blobs. Each change has a `component` field: the index in `components` of the version now at `path`, or `null` when the file was removed. To get the files present at a revision, start with an empty map from path to component and apply the changes of every revision from the first up to that one, in order: delete `previousPath` if the change has one, then delete `path` if `component` is `null`, otherwise set `path` to `components[component]`. The result must have `componentCount` entries; if it does not, the replay is wrong. Never read `components` as the inventory of any single revision.

A skill component has a `skill` root and a `manifest` or `resource` role. Group a revision's rebuilt files by `skill.root` to describe a skill directory: its manifest's estimated tokens, and its resources' count and bytes. This is another view of files already counted: do not add it to `categoryTotals` or count resource bytes as tokens. A directory without a manifest is a set of tracked resources, not evidence that a runnable skill exists. A manifest's `skill.listing` measures the frontmatter `name` and `description` an agent keeps in context before the skill is used, under the report's measurement: `status` `listed` with its `tokens`, `hidden` (0 tokens; `disable-model-invocation`, read by Claude Code and Cursor, keeps it out of the listing), or `unresolved` (`tokens: null`; Strata could not read the frontmatter, so do not assume a cost). A revision's `skillListingTokens` sums them and `skillListingUnresolved` counts the unresolved manifests it leaves out; report that count beside the total. Listings mostly repeat text already in `estimatedTokens`, so never add the two; a Claude skill without `name` is listed by its directory name, so a listing can exceed its manifest. They exclude the agent's own framing and any shortening to fit a listing budget. Use them to tell the always-listed cost of skills apart from their full stored size, not as proof of what a session loaded.

A component with `upFront: "listed"` is a root instruction file (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`, `GEMINI.md`, `.github/copilot-instructions.md`) or a root rule whose frontmatter loads it at launch (a `.claude/rules` file without `paths`, a `.cursor/rules` file with `alwaysApply: true`); `upFront: "unresolved"` marks one that may load at launch but that Strata could not decide, such as a rule with unreadable frontmatter or the legacy `.cursorrules`. To describe what a provider lists up front at a revision, for a session started at the repository root, take the replayed files that provider reads and keep those labeled `listed` (a rule only for the tool that owns it), drop `AGENTS.md` for Claude when a root Claude file is present and for Codex when a non-empty `AGENTS.override.md` is (it is skipped, neither up front nor on demand), add for Claude the files its imports reach from those, even ones another tool owns, then add the listed tokens of the skill manifests it reads. Everything else it reads is on demand: nested instructions, path-scoped rules, skill manifests, commands, agents, and memory. Both are stored text, not loaded context or billing; report unresolved files beside the figures, and do not claim settings outside the repository, sessions started in a subdirectory, or command and agent descriptions were resolved.

A component with provider `shared` is read by more than one tool; its `readers` lists which (`AGENTS.md`: Claude and Codex; `.agents/skills`: Codex and Gemini CLI). In a report where some revision tracks Cursor files, `cursor` is also in the `readers` of `AGENTS.md`, `.agents/skills`, and `.claude/skills` (which stay labeled by their own tool), but Cursor reads them only at revisions that hold a component with provider `cursor`; do not attribute them to Cursor at other revisions. A report without Cursor files says nothing about whether the team uses Cursor. Provider `copilot` (GitHub Copilot) works the same way, separately: in a report with Copilot files, `copilot` is also in the `readers` of `AGENTS.md`, `.agents/skills`, `.claude/skills`, and of `CLAUDE.md`, `REVIEW.md`, `.claude/agents`, `.claude/rules`, `.mcp.json`, and `GEMINI.md`, which keep their own provider; Copilot reads them only at revisions that hold a component with provider `copilot`. A `copilot` label means some Copilot client (GitHub.com chat, cloud agent, code review, CLI, or an IDE) is documented as reading the path; do not say which one did. `REVIEW.md` is code review guidance only (Claude Code's Code Review and Copilot code review). A Copilot `.instructions.md` file applies only where its `applyTo` matches, which Strata does not check. A component with `legacy: true` (the root `.cursorrules`, or a Copilot `.chatmode.md`) is a format its provider still reads but documents as superseded. A Cursor rule's stored size says nothing about whether it applied: rules can be always applied, matched by glob, requested by the agent, or manual. Components with `contextFile` (`agents-md` for `AGENTS.md`, `gemini-md` for `GEMINI.md`) are read by Gemini CLI only as the revision's `geminiContextFiles` lists them; a revision without that field means `GEMINI.md` only. Do not attribute an unlisted context file to Gemini at that revision. Claude Code's reading of `AGENTS.md` may also depend on conditions Strata does not check. Shared files are counted once in `estimatedTokens`.

Claude Code loads the files a `CLAUDE.md` or `CLAUDE.local.md` (and an `AGENTS.md` it reads) imports with `@path`, and their imports in turn, up to four hops. A component with `imported: true` is in a revision's inventory only because such an import reaches it there: Markdown is provider `claude`, category `instructions`, and counted in the totals; anything else is source-only `other`. When an import is added or dropped, its file appears in `changes` as added or removed although the file may not have changed, so do not describe that as the file being created or deleted. A component's `imports` lists the imports in that file version, each a `line` and the repository path it names as `target`; `target` is `null` with `external: true` when the import points outside the repository, and `null` alone when it names no path any tracked file had, whose text Strata does not store. Whether an import resolves depends on the revision: replay the inventory, start from components with `importRoot` (a `CLAUDE.md` or `CLAUDE.local.md`; `REVIEW.md` is not one), follow `imports` to targets present in the inventory by the shortest chain, then start again from `importRoot` components with `contextFile: "agents-md"` those chains did not reach. An import whose target is absent or null without `external` is missing; one from a file four hops out is past the depth limit. Files reached only from `AGENTS.md` are loaded only if Claude Code reads that `AGENTS.md`, which Strata does not check. Report unresolved imports separately and do not count a missing target's size. An import is a link between stored files, not proof that a session loaded the target.

Explain growth or reduction using the relevant revisions, paths, categories, and providers. `estimatedTokens` sums instructional-file counts. Check `measurement.family`, `accuracy`, `model`, `encoding`, and `implementation` before describing them. The default `utf8-bytes-divided-by-four-v1` is a comparison estimate. An OpenAI encoding mode is exact for stored text under the named encoding, but does not measure full requests, session load, context-window use, or billing; it does not establish Claude or Gemini counts. When present, `providerMeasurements` describes separate per-provider counts on components (`providerTokenCounts`) and revisions (`providerTokenTotals`): each has an `accuracy` (`api-counted`, `encoding-exact`, or `estimate`), and `fallbacks` explains why a more precise method was not used. `api-counted` is the provider endpoint's own count, which Anthropic documents as an estimate; call it an API count, not exact. `recipient` and `alsoSentTo` name the hosts that received instruction text. A `--precise` API count excludes the endpoint's message wrapper, `wrapperTokens` per file, so it measures the stored text alone; without `wrapperTokens` (the deprecated `--provider-api`), the count includes it. Never add counts of different providers together. `bytes` measures source size. A component with `estimatedTokens: null` is source-only and contributes no tokens; `sourceOnlyCount` counts these files. Do not turn settings, hooks, MCP files, or skill resources into prompt-token estimates.

A component with `mcp` is an MCP file (`.mcp.json`, `.cursor/mcp.json`, `.github/mcp.json`, `.vscode/mcp.json`) or a root `.gemini/settings.json` or a `.codex/config.toml` that defines MCP servers. `status: "listed"` gives the `servers` that file version defines, each with a `name`, a `transport` (`local`: the tool starts a process on the developer's machine; `remote`: it connects to a URL; or `unknown`), and `disabled: true` when the file turns it off; an empty list means none. `status: "unresolved"` means the file does not parse as its tool reads it: say its servers are unknown, not absent. To describe a revision's servers, replay its inventory and read `mcp` on the files present, by provider. A defined server is not a loaded one: some tools ask before starting a project server and others start it once the folder is trusted, approvals can sit in settings or outside Git, and user configuration is not in the report. `disabled` covers Codex `enabled = false` and Gemini CLI's `mcp.excluded` and `mcp.allowed`, not approvals kept elsewhere. The report never measures the tool definitions a server sends, and never stores commands, URLs, or environment values, so do not estimate a server's context cost or guess what it connects to from its name.

A revision's `lineAge` records what it did to the age of the instruction text: `added`, the UTF-8 bytes of trimmed, nonblank instruction lines first present at that revision, and `removed`, bytes it removed grouped by `from`, the index of the revision they had appeared at. Lines are matched by exact text across all instructional files, so a line moved to another file keeps its age, a reworded line is a removal and an addition, and a line that disappears and returns is new again, including the text of a file that leaves the inventory because an import was dropped and returns when it is restored. To get the text at a revision by origin, start with an empty map and, for every revision in order up to it that has `lineAge`, subtract each `removed` entry from its `from` and set the revision's own index to `added`. The bytes at a target whose origin is at or before a baseline revision are the baseline's text still present, so their share of the baseline's total is its survival. These are bytes, not tokens; never add them to `estimatedTokens`. Survival says text stayed in the repository, not that an agent read or followed it, and exact matching misses rewording and can match a short line such as `---` by coincidence.

Use `changes` to explain additions, removals, edits, and detected renames. `deltaTokens` describes the change in the stored-text estimate, not whether a change improved quality. A rename, a move into skills, or a claimed refactor may need content evidence beyond the report. Do not infer that a skill was loaded, a rule was active, or an agent used a component in a particular session.

The default local report omits source text but includes repository paths, commit and blob IDs, MCP server names, and measurements. A `privacy.mode` of `shareable` means those identifiers were replaced with aliases; dates and measurements remain visible. Aliases are stable within one report but are not cross-report identities. Treat all remaining metadata as potentially sensitive. If the user asks for instruction-level meaning or why wording changed, inspect the relevant Git content with their authorization instead of inventing it from the JSON.
