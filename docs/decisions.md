# First-release decisions

Recorded 2026-10-08. These choices describe the current implementation, not a package publication or claim about runtime context.

## Name and command

The npm package name is `context-strata`; its executable is `strata`. Direct queries to the npm registry on 2026-10-08 returned 404 for `context-strata` and `strata@0.20.1` for `strata`. A 404 is not a reservation. Version 0.1.0 is prepared but unpublished; verify availability again before release. The intended command after publication is `npx context-strata analyze . --output report.html`.

## License and contributions

Strata uses the OSI-approved MIT license, chosen to allow broad use and redistribution with a short attribution requirement. The repository has a contribution guide and a security-reporting path. The packaged runtime dependency `d3-hierarchy` has a separate ISC license, which remains embedded in offline HTML reports alongside its code.

## Measurement

By default, stored instructional text uses Strata's `utf8-bytes-divided-by-four-v1` comparison estimate: `ceil(UTF-8 bytes / 4)` per file, then sum. An opt-in `--tokenizer openai-cl100k_base` or `openai-o200k_base` uses local `js-tiktoken@1.0.21` to count valid UTF-8 text under that encoding. `--model` maps the explicitly supported OpenAI model names (`gpt-4`, `gpt-4o`, `gpt-4.1`, `gpt-5`, `o3`, `o4-mini`) to the encoding documented in [OpenAI's tiktoken model map](https://github.com/openai/tiktoken/blob/main/tiktoken/model.py). Like tiktoken's prefix table, names starting with `gpt-5`, `gpt-4.1-`, `gpt-4o-`, `o3-`, or `o4-mini-` use `o200k_base` and names starting with `gpt-4-` use `cl100k_base`, so variants such as `gpt-5-codex` resolve. Other names, including `gpt-oss-` models, whose `o200k_harmony` encoding Strata does not ship, fail rather than guessing. The count is exact for the selected text encoding, but excludes message framing, special-token handling, actual loaded context, and billing. Text that spells a special token, such as `<|endoftext|>` in a file about language models, is counted as ordinary text rather than rejected. Counting is done per pattern piece with a cache of distinct pieces, which gives the same total as encoding the whole text (see [the benchmark notes](benchmark.md)). It does not claim accuracy for Claude or Gemini. One encoding is applied to every instructional file and every revision in a report. These default and local modes make no network request or content transfer. Structured config and supporting resources are source bytes only. See [the tokenizer study](tokenizers.md) for evidence.

`strata analyze --precise` is the explicit opt-in for precise per-provider counts. It needs no other flag: each provider is counted with the most precise method available, tried in this order, and the report and run output say which one was used and why each earlier one was skipped.

| Provider | 1. Signed-in account | 2. API key | 3. Local exact | 4. Estimate |
| --- | --- | --- | --- | --- |
| Claude (default `claude-opus-5-5`, `--claude-model`) | `ant auth login` profile, through `ant auth print-credentials --access-token`; Anthropic count endpoint. With neither that nor `ANTHROPIC_API_KEY`, a ready `gcloud` account; Vertex AI `count-tokens:rawPredict` | `ANTHROPIC_API_KEY`; Anthropic count endpoint | none exists | byte estimate |
| Gemini (default `gemini-3.8-flash`, `--gemini-model`) | `gcloud` account with a project (`GOOGLE_CLOUD_PROJECT` or `gcloud config`), through `gcloud auth print-access-token`; Vertex AI `countTokens` in `GOOGLE_CLOUD_LOCATION` (default `global`) | `GEMINI_API_KEY` or `GOOGLE_API_KEY`; Gemini API `countTokens` | none exists | byte estimate |
| Codex (default `gpt-5`, `--codex-model`) | not used | not used | `js-tiktoken` encoding for the model | byte estimate |

A provider with no recognized instructions anywhere in the analyzed history is skipped entirely: its CLI is not run, no credential is looked up, and the report has no count column or metadata for it. For Claude, `gcloud` is consulted only when neither an `ant` account nor `ANTHROPIC_API_KEY` is available, so Claude text never goes to Google Cloud when an Anthropic credential exists. Strata uses a signed-in account only through the provider's own CLI, which prints a short-lived access token; it never reads credential files. Two sign-ins are deliberately not used. A Claude Code subscription login is for Claude Code and Claude.ai only, and Anthropic does not permit other tools to use its OAuth tokens; an `ant auth login` profile is an API credential that Anthropic's SDKs and CLI share. Gemini CLI's Google sign-in reaches the Code Assist service, whose terms forbid third-party tools from using it, and Gemini CLI has no count command; a `gcloud` account calling Vertex AI is the supported route. Codex is counted locally because OpenAI's encodings are published and exact for stored text, so a signed-in ChatGPT account or `OPENAI_API_KEY` would only add a transfer. A method that fails during the run, such as a rejected token, is discarded whole and the next is tried, so one provider's counts never mix methods. Every instruction version is read once before anything is sent: blank files count as zero without a request, a provider whose files are all blank sends nothing (not even the wrapper probe) and names no recipient, and a version that is not valid UTF-8 has no text count, so its providers use the byte estimate for every file and send nothing. Each provider's metadata records its `accuracy` (`api-counted`, `encoding-exact`, or `estimate`), its `credential` source (never the credential), the `recipient` host when text left the machine, and `fallbacks`. Before sending, the CLI prints which host will receive how many instruction file versions; this notice is shown even with `--quiet`.

A count endpoint counts a request, not a file, so each count includes the tokens of a one-message wrapper (on 2026-10-15, 8 for `claude-opus-5-5` and 1 for `gemini-3.8-flash` through the Gemini API). Strata measures the wrapper once per model by counting the one-letter text `a`, which is one token in any byte-level tokenizer, and subtracts the count less one from every file, clamped at zero. This assumes the wrapper does not merge with the file's first or last characters; it is recorded as `wrapperTokens` so a reader can add it back. Rate limits (429), overload (529), timeouts (408), and server errors are retried up to six times with backoff, honoring `retry-after` up to 60 seconds; only a method that still fails falls back. Remote counts are cached between runs per endpoint family, model, and Git blob, and the wrapper count per endpoint family and model, so a rerun sends only new file versions; a model name ending in `-latest` is an alias that moves to new models, so its counts are not cached; the cache file is owner-readable and holds no paths or text. `--dry-run` resolves credentials and reports each provider's method and what would be sent, without counting or sending. `strata diff --precise` uses the same methods and reports each provider's totals at the base and head commits (PR delta schema version 5 added `providerMeasurements` and `providerTotals`). Access tokens and keys are held in memory for the run only and never written to reports or output.

`strata analyze --provider-api` is the earlier, deprecated form; it prints a deprecation warning and otherwise behaves as before. It requires a Claude model and a Gemini model, uses `ANTHROPIC_API_KEY` and `GEMINI_API_KEY` (or `GOOGLE_API_KEY`), and sends each recognized Claude or Gemini instruction blob to its matching count endpoint as one user text message. Shared instructions are counted separately for both selected provider models. `--codex-model` optionally adds a local OpenAI encoding count for Codex instructions. Provider counts are cached by provider, model, and blob; the same provider/blob is requested once across history. Separate provider counts are never added to each other or to the generic estimate. The legacy `estimatedTokens` history remains the default byte estimate. `--dry-run` and `--no-cache` are rejected with `--provider-api`.

## History extraction

Analysis reads the whole first-parent history from one streamed `git log --first-parent --diff-merges=first-parent --raw -M` process, which needs Git 2.31 or newer. Each commit's raw diff against its first parent updates an in-memory inventory of recognized regular files; symlinks and submodules are never tracked. The same diff shows each submodule entry being added or removed, so the submodules present at the last commit, and the commit each records, are collected without another Git command. `--ignore-submodules=none` keeps settings such as `diff.ignoreSubmodules` from hiding them. Renames are the ones Git reports in that diff, and only a rename between two recognized paths is labeled as such. Blob sizes come from `git cat-file --batch-check`. Blob content is read, in bounded batches, for every instructional file version, because [instruction age](#instruction-age) matches their lines, and for three kinds of other file: the root Gemini settings, to resolve `context.fileName`; skill manifests, to measure their listing; and Claude instruction files and the Markdown their imports reach, to resolve `@path` imports. Each instructional version is reduced to counts of its lines as soon as it is read, with each distinct line's text kept once, so memory grows with the distinct lines plus a few bytes for each line of each distinct version, not with the history's text. Settings, MCP, and other source-only files are otherwise read only where a section below says so. For the paths imports name that no path rule recognizes, one more `git log --first-parent` limited to those paths gives their history, and the history is replayed to decide, commit by commit, which of them the imports reach; see [Claude imports](#claude-imports). Imports nest at most four hops, so there are at most four such rounds, and none when no instruction file has an import. `strata diff` lists the two commit trees directly and shares the same classification and measurement code.

Analysis keeps one running inventory and records, for each revision, only what that commit changed. It never materializes a per-revision file list, so memory and report size grow with the number of distinct file versions plus the number of revisions, not with revisions multiplied by tracked files.

## Report contract and privacy

Schema version 9 stores each distinct file version once and each revision as a delta. A top-level `components` table holds one entry per distinct path-and-blob pair across the whole history, ordered by path. A revision carries its `componentCount`, `categoryTotals`, `estimatedTokens`, and `changes`; it no longer repeats its inventory, and `skillGroups` is no longer stored. Every change has a `component` field: the index in `components` of the file version now at `path`, or `null` for a removal. On one local repository with 181 revisions this cut the HTML report from 57.5 MB to 1.5 MB.

To rebuild the inventory at a revision, start empty and apply every revision's changes in order up to it: drop `previousPath` when present, then drop `path` if `component` is `null`, otherwise set `path` to that component. `src/expand.ts` implements this rule, the HTML report embeds the same function, and a fixture test checks the replayed inventory of every revision against a direct listing of that commit's tree. Skill bundles are derived from the rebuilt inventory by grouping components on `skill.root`. Stored totals let a consumer chart history without replaying anything.

Schema version 8 added Gemini CLI to provider labels and optional `providerTokenCounts` on instruction components, with separate `providerTokenTotals` on revisions; later versions keep both. Each provider count carries its provider, explicit model, method, implementation/API version, and `api-counted` or `encoding-exact` accuracy label. Provider labels identify recognized path conventions, not exclusive runtime support; a shared file is stored once and receives separate counts per selected provider that reads it.

Schema version 10 adds `readers` to shared components: the providers documented as reading that path, `["claude", "codex"]` for `AGENTS.md` and `["codex", "gemini"]` for `.agents/skills`. Claude Code's reading of `AGENTS.md` remains an unresolved condition, as before. Files under `.agents/skills/<name>/`, labeled `codex` in version 9, are now `shared`. Gemini CLI reads `AGENTS.md` and `GEMINI.md` according to `context.fileName`, which can change between revisions while the files do not, so that condition is split between the file and the revision. Those components carry `contextFile: "agents-md"` or `"gemini-md"`; a revision whose repository-root `.gemini/settings.json` sets `context.fileName` carries `geminiContextFiles`, the labels it names, and omits it otherwise, meaning `GEMINI.md` only. The labels are deliberately not file names, so they cannot match an aliased path in a shareable report, and unrecognized configured names are not stored. `providerReads` in `src/provider-view.ts` is the one rule for whether a provider reads a component at a revision; analysis totals, provider views, and the report's provider columns all use it. In provider API mode, a context-file version is sent to Gemini only if some revision where Gemini reads it contains it.

Schema version 11 adds what `--precise` needs to label its choices: a provider count's `accuracy` may be `estimate`, with a `null` model, when no account, key, or local tokenizer was available; and each `providerMeasurements` entry may carry `credential`, `recipient`, `alsoSentTo` (hosts that received text from a method that then failed), `wrapperTokens`, and `fallbacks`. A fallback for a failed count gives the provider's short error code, such as `BILLING_DISABLED`, and a hint for that endpoint, never the provider's error message, which can name the Google Cloud project.

Schema version 12 adds `submodules`: one entry per submodule present at the last revision, sorted by `path` and omitted when there are none. A submodule entry stores only a commit ID from another repository, and agent configuration is sometimes kept in one and copied into an ignored directory by a script, so a report could look complete when it is not. Each entry's `configFiles` is the number of regular files in the submodule at the recorded commit whose path is recognized either inside the submodule (a template with its own `.claude/`) or where it is mounted in the parent (a skill kept as a submodule at `.claude/skills/<name>`), found by listing that commit's tree in the submodule's own checkout. It is `null` when the submodule is not checked out or lacks that commit. The checkout must resolve inside the parent and its top level must be the submodule directory itself, so an empty directory is not mistaken for the parent repository. These Git commands run without the parent's `GIT_DIR`-style variables and with `GIT_NO_LAZY_FETCH=1`, so with Git 2.44 or newer a partial clone is never fetched from; older Git ignores that variable. The count says only that the submodule holds files matching the path rules; Strata does not analyze them, and the user can run Strata on the submodule instead. The result depends on which submodules are checked out, so the same commit can give different counts on different machines. The HTML report shows a warning above the timeline and the command line prints a note. Both name submodules with recognized files, at most five, and give only a count for those that could not be checked; submodules without recognized files are left out, so vendored libraries add no noise. The command line escapes control characters in submodule paths. The static SVG image carries no submodule note. A shortened, illustrative JSON shape:

Schema version 13 adds a `listing` to the `skill` object of each skill manifest and `skillListingTokens` and `skillListingUnresolved` totals to each revision; see [Skill listings](#skill-listings). Revisions from earlier versions have neither.

Schema version 14 adds the `cursor` provider for `.cursor/rules/**/*.mdc`, the root `.cursorrules`, `.cursor/commands/*.md`, `.cursor/mcp.json`, `.cursor/skills/<name>/`, the root `.cursorignore`, and other candidate files in Cursor's folders under `.cursor/`. Only those folders and top-level JSON are inventoried as `other`, because projects keep unrelated notes under `.cursor/`. Cursor also reads files that belong to other tools: `AGENTS.md`, `.agents/skills`, and `.claude/skills`. Cursor needs no file in the repository, so Strata treats it as reading them only at a revision that tracks Cursor configuration, meaning a revision with at least one component labeled `cursor`. The rule is in `providerReads`, derived from each revision's components, so it needs no stored field and survives `--shareable`. Where some revision has Cursor configuration, Cursor joins the `readers` of `AGENTS.md` (`["claude", "codex", "cursor"]`) and `.agents/skills` (`["codex", "cursor", "gemini"]`), and `.claude/skills` components keep provider `claude` with `readers: ["claude", "cursor"]`. Where none does, `readers` is exactly as in version 13, so a Claude-only report has no Cursor label anywhere. So `cursor` in `readers` means Cursor can read the path, not that it read that file version: a version present only before Cursor configuration appeared still lists it. Cursor's condition is resolved per revision, like Gemini CLI's `context.fileName`, which is carried by `contextFile` rather than `readers`. Cursor also loads `.codex/skills`, which current Codex documentation does not list, so the path stays Codex `other`. A component may carry `legacy: true`, set only on the root `.cursorrules`: Cursor still reads it but documents `.cursor/rules` as its replacement, so the report keeps it in `rules` and labels it instead of hiding the difference. The label is not a path, so it survives `--shareable`, and it identifies the root `.cursorrules` behind its alias. Rule frontmatter (`alwaysApply`, `globs`, `description`) is stored text like any other and is not interpreted, so the report does not claim which rules were active. Cursor has no `--precise` count; its files keep the report's measurement. Reports from version 13 and earlier recognize no Cursor files. [The adapter study](next-adapter.md) records the evidence for each pattern.

Schema version 15 adds the `copilot` provider for GitHub Copilot: `.github/copilot-instructions.md` as instructions, `.github/instructions/**/*.instructions.md` as rules, `.github/prompts/*.prompt.md` as commands, `.github/agents/**/*.md` (except `README.md`) as agents, `.github/skills/<name>/` as skills, `.github/mcp.json` and the root `.vscode/mcp.json` as tools, and the root `.github/hooks/*.json`, `.github/copilot/settings*.json`, and the `copilot-setup-steps.yml` and `copilot-code-review.yml` workflows as settings; the tools and settings files are source-only. Nothing else under `.github/` is inventoried, so ordinary workflows, issue templates, and `CODEOWNERS` stay out of the report. A `.chatmode.md` inside `.github/agents` carries `legacy: true`, because chat modes are the format custom agents replaced; a file in `.github/chatmodes`, which current VS Code reads only when a user setting adds that folder, is source-only `other`. `applyTo`, `excludeAgent`, and `target` frontmatter is stored text, not interpreted. Copilot, like Cursor, needs no repository file and reads other tools' files, so the same rule applies to it separately: at a revision with at least one component labeled `copilot`, Copilot reads `AGENTS.md` (`readers: ["claude", "codex", "copilot", "cursor"]` where both apply), `.agents/skills`, and the Claude and Gemini files it documents reading, which keep their own provider and gain `readers`: `CLAUDE.md` and `.claude/CLAUDE.md`, `REVIEW.md` (at any depth, newly recognized as Claude instructions because [Claude Code's Code Review](https://code.claude.com/docs/en/code-review-customize) reads it), `.claude/agents` and `.claude/rules` (except a `README.md`), and the root `.mcp.json` get `["claude", "copilot"]`; `.claude/skills` gets `["claude", "copilot"]` (with `cursor` where Cursor is configured); and `GEMINI.md` gets `["copilot", "gemini"]`. Gemini CLI's `context.fileName` still decides only Gemini's reading of `GEMINI.md`. Where no revision has Copilot configuration, `readers` is exactly as in version 14. A file keeps its owner's label, rather than becoming `shared`, so adopting Copilot does not move tokens out of the Claude or Gemini CLI totals. `CLAUDE.local.md` and `.claude/settings.json`, from which Copilot reads only hooks, gain no reader. The `copilot` label means at least one Copilot client (GitHub.com chat, the cloud agent, code review, Copilot CLI, or an IDE) is documented as reading the path; the report does not say which. Copilot has no `--precise` count; its files keep the report's measurement and their text is never sent. Reports from version 14 and earlier recognize no Copilot files and no `REVIEW.md`. [The Copilot adapter study](copilot-adapter.md) records the evidence for each pattern.

The actual `categoryTotals` has an entry for every category. Skill components have a `skill` object with directory root and `manifest` or `resource` role. The HTML report's skill-bundle table summarizes those same files, separating manifest token estimates from resource byte sizes; these summaries are not additional measurements. Default HTML and JSON contain commit IDs, dates, paths, provider/category labels, blob IDs, byte sizes, and estimates. They contain no source text. Paths and blob IDs can still disclose repository structure. HTML and JSON reports are local artifacts; the CLI writes them with mode `0600`. The HTML report carries a Content-Security-Policy that allows only its own inline style and script, so a browser will not load anything from the network on its behalf. The default measurement modes make no network request and upload no content. Explicit `--precise` (or deprecated `--provider-api`) mode sends recognized Claude and Gemini instructional text to the provider APIs it finds credentials for; reports store counts and measurement metadata, not submitted text, credentials, or the Google Cloud project.

Schema version 16 adds Claude `@path` imports: `imports` on each version of an instruction file or reached Markdown file that has any, `importRoot` on a `CLAUDE.md`, `CLAUDE.local.md`, or `AGENTS.md` that has imports (Claude Code starts expanding there; `REVIEW.md` is not a root), and components with `imported: true` for files that are in an inventory only because an import reaches them; see [Claude imports](#claude-imports). Earlier versions neither resolve imports nor include such files, so their totals can be lower for the same history.

Schema version 17 adds `upFront` to components that may be read from the start of a session at the repository root; see [Up-front context](#up-front-context). Earlier versions do not separate up-front text from the rest.

Schema version 18 adds `mcp` to MCP configuration files and to Gemini CLI and Codex settings files that mention MCP servers; see [MCP servers](#mcp-servers). Earlier versions record those files by size alone.

Schema version 19 adds the top-level `lineAgeMethod` and a `lineAge` on each revision that added or removed instruction lines; see [Instruction age](#instruction-age). Earlier versions have no instruction age, and analysis of the same history now reads every instructional file version. It also narrows `shallow`: it is true only when the first revision is a shallow boundary, the commit where a shallow fetch cut the history. A full history in a repository that fetched some other branch shallowly is no longer flagged.

`--shareable` produces schema version 19 with `privacy.mode: "shareable"`. It replaces repository and branch names, commit and first-parent IDs, component and change paths, import targets (with the same aliases as paths, including targets no file has), skill roots, MCP server names, submodule paths, and blob IDs with deterministic aliases local to that report. The alias maps are not embedded. Dates, category and provider labels, `readers`, `contextFile`, `legacy`, `imported`, `importRoot`, and `upFront` labels, an MCP server's `transport` and `disabled`, `lineAge`, counts, byte sizes, estimates, change kinds, and timeline shape remain visible. Some labels narrow an alias to a well-known path: `legacy` is set only on the root `.cursorrules` and on a Copilot `.chatmode.md` in `.github/agents`, as Claude `tools` is only the root `.mcp.json`, and `upFront` is set only on a few root file names and on rules in the root `.claude/rules` and `.cursor/rules`. The default local report is unchanged. Shareable means reduced identifier exposure, not guaranteed anonymity; inspect before publishing.

## MCP servers

An MCP file's JSON is configuration, not prompt text, and its size says nothing about the tool definitions a server sends once it starts. Strata never starts a server, so it does not measure those. What the file does state is which servers the project defines, so each version of an MCP file carries `mcp`: `status` `listed` with its `servers`, or `unresolved` when the file does not parse the way its tool reads it. A server has its `name`, a `transport` of `local` (the tool starts a process: a `command`, or a `type` of `stdio` or `local`), `remote` (it connects to a URL: `url` or `httpUrl`, or a `type` of `http`, `streamable-http`, `sse`, or `ws`), or `unknown` (also when an entry without a `type` has both a command and a URL, since tools disagree on which wins), and `disabled: true` when the file turns it off: Codex `enabled = false`, or a name Gemini CLI's `mcp.excluded` lists or its `mcp.allowed` leaves out (`excludeMCPServers` and `allowMCPServers` in older settings). Commands, arguments, URLs, headers, and environment values are never read into the report, because committed MCP files often hold credentials.

| File | Servers read from | Syntax accepted |
| --- | --- | --- |
| Root `.mcp.json` (Claude, also Copilot) | `mcpServers` | strict JSON |
| `.cursor/mcp.json` | `mcpServers` | JSON with comments and trailing commas |
| `.github/mcp.json` | `mcpServers`, or, when it is absent, the top-level entries that have a `command`, `url`, or `type`, as Copilot CLI accepts | strict JSON |
| `.vscode/mcp.json` | `servers` | JSON with comments and trailing commas |
| Root `.gemini/settings.json` | `mcpServers`, only when the file has it; nested settings are not read, as for context files | JSON with comments |
| `.codex/config.toml` | `[mcp_servers.<name>]` tables and dotted `mcp_servers.<name>.<key>` keys, only when the file has them; `enabled = false` disables | a TOML subset; inline `mcp_servers` tables are unresolved |

Where a tool does not document its syntax, Strata accepts the stricter one, so a file that only a lenient parser reads is unresolved rather than listed. Only syntax is checked: a server whose values its tool would reject, such as one with neither a command nor a URL, is still listed. An unresolved file's servers are counted apart, never as none. A defined server is not a loaded one: Claude Code asks before starting project servers unless settings approve them (`enableAllProjectMcpServers`, `enabledMcpjsonServers`, and `disabledMcpjsonServers` in `.claude/settings.json`, which Strata does not resolve), Copilot CLI, Codex, and Gemini CLI start project servers once the folder is trusted, without asking for each one, and user and global configuration is outside Git. The HTML report lists the servers in a collapsed panel that follows the provider tab, and the comparison counts them by file and name, so a server moved to another file is a removal and an addition, and one server defined for two tools counts twice.

## Skill listings

Claude Code, Codex, Copilot, Cursor, and Gemini CLI keep a skill's name and description in context and read the rest of its `SKILL.md` only when the skill is used. The manifest's `estimatedTokens` measures the whole stored file, so a skill's stored size says little about what it costs before it runs. A manifest's `skill.listing` measures that listed part: the frontmatter `name` and `description` values joined by a newline, counted with the report's measurement. The text boundary follows [Claude Code's skill reference](https://code.claude.com/docs/en/skills), [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Gemini CLI skills](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/skills.md), [Cursor skills](https://cursor.com/docs/context/skills), and [Copilot skills](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/add-skills):

- A Claude skill without `name` is listed by its directory name, and one without `description` by the first non-empty line of its body, taken as stored (a Markdown heading keeps its `#`), as the reference describes. `when_to_use` is appended to the description, and the two are cut together at 1,536 characters (Unicode code points). `disable-model-invocation: true` leaves the skill out of the listing: its `status` is `hidden` and `tokens` is 0.
- Codex, Copilot, Cursor, and Gemini CLI skills, including shared `.agents/skills`, must set both `name` and `description`; Claude-only fields are ignored. Cursor also leaves out a skill with `disable-model-invocation: true` until it is invoked by name, so a `.cursor/skills` manifest that sets it is `hidden`. A manifest keeps one listing, by the rules of the tool that owns its folder: Claude Code's for `.claude/skills` and Codex and Gemini CLI's for `.agents/skills`, which ignore `disable-model-invocation`. Cursor's and Copilot's own listings of those skills are not measured separately and can differ; the HTML Cursor and Copilot views say so beside their skill tables.
- Frontmatter counts only when the file's first line is `---` and a later `---` line closes it. Strata reads a subset of YAML: top-level keys whose values are plain scalars over one or more lines, single-line quoted scalars, or literal and folded block scalars. A field Strata needs in another form, such as a flow sequence or a plain value containing `: `, a duplicate key, an unclosed block, a missing required field, or a manifest that is not valid UTF-8 makes the listing `unresolved`, with `tokens: null`. Strata does not guess what an agent would do with frontmatter it cannot read; Claude Code, for instance, loads a skill whose YAML does not parse with no fields set.

A listing has `status` `listed`, `hidden`, or `unresolved`. It is measured separately from the manifest's stored text and never added to it or to any total: `skillListingTokens` on a revision sums the listings of the manifests present, `skillListingUnresolved` counts the unresolved ones it leaves out, and provider views recompute both from the files they show. A listing mostly repeats text already in the manifest's count, but not always: a Claude skill without `name` is listed by its directory name, which is not in the file, so a short manifest's listing can exceed its stored tokens. Totals always state how many unresolved manifests they leave out, so fixing a broken frontmatter is not mistaken for a new cost; Claude Code still lists such a skill, with fields Strata cannot know. Because the default name comes from the directory, renaming a Claude skill directory can change its listing without changing the file.

What a listing does not measure: the agent's own wrapper around each entry; the path Codex lists beside each skill; Codex shortening descriptions to fit `skills.max_context_tokens`; Claude Code dropping descriptions of its least-used skills when the whole listing exceeds its budget (1% of the context window by default, changed with `skillListingBudgetFraction` or `SLASH_COMMAND_TOOL_CHAR_BUDGET`), a per-entry cap changed with `skillListingMaxDescChars`, and `skillOverrides` set to `name-only`; skills disabled outside the repository or by `agents/openai.yaml`; precedence between skills of the same name; and user or plugin skills. `--precise` does not send listing text anywhere: listings use the report's measurement, the byte estimate by default. In an HTML view showing a provider's own counts, manifest tokens change but listings do not, so the view names the listings' measurement and says the two are not comparable. No listing text is stored in the report.

The HTML report and `strata diff` show listings wherever they show a manifest's stored tokens: the skill-bundle table and its heading, the treemap detail line and inventory token cell of each manifest, and the comparison, which gives the listed-token change between two revisions and, per changed manifest, its listing change. A manifest's listing change is a signed token difference when both sides are listed, and otherwise the state at each side, such as `none → 12` for an added manifest or `unresolved → 3`, so a status change is never shown as a token difference. The history chart, SVG image, and badge keep to stored-text totals.

## Up-front context

A repository's stored total mixes text an agent keeps for the whole session with text it reads only for some work. For each provider, Strata splits what that provider reads at a revision (by `providerReads`) into two stored-text figures, for a session started at the repository root:

- **Up front**: the root instruction files it reads, its own root rules that load at launch, and, for Claude Code, every file `@path` imports reach from those (by the [import rules](#claude-imports), up to four hops), plus the [listings](#skill-listings) of the skill manifests it reads. The figure is the files' stored-text tokens plus the listed tokens.
- **On demand**: the stored-text tokens of every other file it reads, for later in the session, for a session started in a subdirectory, or for other work: nested instruction files, path-scoped rules, skill manifests (whose listings are already up front), commands, agents, memory, `REVIEW.md`, and `.gemini/system.md`.

A root `AGENTS.md` that a default skips, as described below, is in neither figure and is counted apart as skipped. Up-front files, on-demand files, and skipped files add up to the provider view's stored total, with one exception: Claude Code loads whatever its imports reach, so a file another tool owns that a Claude import reaches, such as `GEMINI.md`, is up front for Claude although the Claude view does not list it. Listings are extra, because they mostly repeat text the manifests count.

Both are stored text under the report's measurement, never provider counts: not loaded context, which also holds the tool's own prompt, user and organization files, and conversation, and not billing tokens.

The boundary follows each tool's documentation. Claude Code loads `CLAUDE.md`, `.claude/CLAUDE.md`, and `CLAUDE.local.md` in the directory it starts in and above, with their imports, and the rules in `.claude/rules` without `paths` frontmatter; files in subdirectories, path-scoped rules, and rules in nested `.claude/rules` folders load when it works there ([memory](https://code.claude.com/docs/en/memory)). By default it reads a root `AGENTS.md` only when none of those three files exists at the root, so `AGENTS.md` is up front for Claude only then, or when an import reaches it. Codex reads, at the root, a non-empty `AGENTS.override.md` instead of `AGENTS.md` ([AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)); nested files below the starting directory are not read. Gemini CLI reads its context files in the workspace directory and its parents at startup, and those in subdirectories when a tool touches them ([context files](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md)), so only the root `GEMINI.md` and, when `context.fileName` names it, `AGENTS.md` are up front. Cursor applies the root `AGENTS.md` and rules with `alwaysApply: true` to every chat, and other rules by glob, by agent request, or by mention ([rules](https://cursor.com/docs/rules)). Copilot applies `.github/copilot-instructions.md` to every request in the repository, and reads the root `AGENTS.md`, `CLAUDE.md` (and `.claude/CLAUDE.md`, as Strata's Copilot readers do), and `GEMINI.md`; `.instructions.md` files apply only to files their `applyTo` matches, and the nearest nested `AGENTS.md` wins for work in its folder ([repository instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). `REVIEW.md` is read only by code review, and `.gemini/system.md` only with `GEMINI_SYSTEM_MD` set.

The split is derived from labels, so it needs no per-revision field and survives `--shareable`. A component carries `upFront: "listed"` when its readers may keep it from the start: the root `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`, `GEMINI.md`, and `.github/copilot-instructions.md`, a rule directly under the root `.claude/rules` (at any depth inside it) without `paths`, and a root `.cursor/rules` rule with `alwaysApply: true`. `upFrontContext` in `src/up-front.ts`, which the HTML report embeds, applies `providerReads`, the `AGENTS.md` and override defaults, and the imports. A rule's frontmatter decides only for the tool that owns it: Copilot reads `.claude/rules` with its own rules, so those files are on demand in the Copilot figure. Rule frontmatter is read with the [skill-listing YAML subset](#skill-listings); for Claude, a `paths` string, flow list, or block list scopes the rule. Rule content is read for this even when the measurement needs only sizes.

`upFront: "unresolved"` marks a file that may be read up front but is counted on demand, and the report counts these beside the figures: a root rule whose frontmatter Strata cannot read, or whose `paths` or `alwaysApply` value it cannot interpret (Claude Code loads a rule whose YAML does not parse as if it had no `paths`, but Strata cannot tell a YAML error from YAML outside its subset), and the root `.cursorrules`, whose loading Cursor's current documentation no longer describes. A skill manifest that a Claude import reaches is counted both as an up-front file and by its listing.

What the split does not resolve: sessions started in a subdirectory, which load that directory's files and its parents'; settings outside the repository, such as Claude Code's **Project instructions** setting that reads `AGENTS.md` beside `CLAUDE.md`, `claudeMdExcludes`, Codex's `project_doc_fallback_filenames`, and user, organization, or managed instructions; Codex's 32 KiB `project_doc_max_bytes` cap on instruction files; which Copilot client is in use; Copilot's `.claude/rules` and `.instructions.md` files whose `applyTo` matches every file; and the names and descriptions some tools list up front for commands and agents, which Strata does not measure. The figure also leaves out imports in files Copilot or another tool reads, which only Claude Code expands.

The HTML report's **At session start** panel shows, for the selected revision, each provider's up-front files, their tokens, the listed skill tokens, the up-front total, and the on-demand total, with the unresolved counts; in a provider view it shows that provider alone and lists the files it keeps up front. It always uses the report's measurement and the whole inventory, whatever the view counts with. The panel also names skipped files. `strata analyze` prints each provider's figures at the last revision, and `strata diff` compares them between two commits. The history chart, SVG image, and badge keep to stored-text totals.

## Claude imports

Claude Code loads the files a `CLAUDE.md` imports with `@path` at launch alongside it, so an instruction file's own size understates what it brings into context, and a configuration split across imported files would otherwise be invisible to Strata. [The analysis scope](analysis-scope.md#claude-imports) lists the parsing and resolution rules; they follow [Claude Code's memory documentation](https://code.claude.com/docs/en/memory#import-additional-files) as read on 2026-10-18, which gives the four-hop limit, resolution against the importing file's directory, escaped spaces, quoted paths, and the code exclusions. The rest of what Strata reads as an import (an `@` at a line start or after whitespace, a removed `#` fragment, and which first characters make a path) is Strata's reading of Claude Code's behavior, not documented, and the Markdown structure Strata recognizes is a documented subset.

The decisions that shape the data:

- **Resolved against Git, per revision.** A target resolves only to a tracked regular file at the same revision. Strata does not know where a repository is checked out, so absolute and home-directory imports are `external` rather than looked up on this machine, and none of their text is stored.
- **Measured where no path rule recognizes the file.** The imported text is loaded at launch like the importing file, so imported Markdown is measured as Claude instructions, in its own component rather than added to the importer. Other files Claude imports, such as `package.json`, are inventoried by bytes: they are loaded as text too, but structured files stay source-only until a text boundary is defined for them. A file that a path rule already recognizes keeps its own labels and is counted once.
- **Recognized files keep their labels.** A file a path rule recognizes is counted once, as that rule says, even when imported, so an imported skill resource or other source-only Markdown file stays source-only. Relabeling a file by revision would let one file version carry two measurements.
- **Membership follows the imports.** An imported file is in the inventory exactly while an import reaches it. Adding or dropping an import therefore adds or removes the file at that revision, and the comparison shows the same, without the file having changed. Imported files are found by a path-limited history read without rename detection (with `log.follow` turned off, since it would turn rename following back on for a single path), so a moved imported file is a removal and an addition. A pathspec also matches files under a directory of that name; only the requested paths are kept.
- **Edges are derived, not stored per revision.** What a file imports depends only on its content, so it is stored once per file version as `imports`: a 1-based line, as evidence, and the resolved target path, never the import text. A target is kept only when some regular file in the analyzed history has that path: an `@` followed by a word that is not a path, such as a person's handle in prose, is still an import to Claude Code, which finds no file, but storing it would put file text into a report that promises paths only. Such an import stays in the list as `missing` with a null target. Whether an import resolves depends on the revision; `importLinks` derives each revision's `links to` edges, with their hop count and status, from the rebuilt inventory alone, so analysis, the HTML report, and a JSON consumer agree, and a shareable report gives the same edges. Roots are chosen by labels, not paths: first Claude instructions not themselves imported, then each `agents-md` context file those chains did not reach, so an `AGENTS.md` that a `CLAUDE.md` imports counts its own imports from the second hop, as Claude Code does.
- **Unresolved imports are listed, not drawn.** `missing`, `external`, and `depth-limit` imports stay in the derived list with their status, and the report lists them first, so a broken import is visible instead of silently absent.

What this does not establish: which files a session loaded. Claude Code asks before loading external imports, skips files it cannot read as text, reads `AGENTS.md` only under conditions Strata does not resolve, and loads nested `CLAUDE.md` files only when it works in their directory. Imports in rules and other files are followed only when an import reaches them. `strata diff` resolves imports in each of its two trees the same way and includes the imported files in its totals; the comparison marks them `imported`, and its summary's file table adds "(imported)" to the change, since a change that only adds or drops an import lists the file as added or removed.

## Instruction age

Instruction age answers how much of a revision's instruction text dates from each earlier period, and how much of an older revision's text is still there, in the spirit of git-of-theseus cohorts. It covers every component with stored text (`estimatedTokens` not null), across all files whatever the provider view; settings, MCP schemas, and other source-only files never take part.

Text is compared as lines. Each line is trimmed (so CRLF endings and indentation do not matter), blank lines are skipped, and the rest are matched by exact text across all instructional files, ignoring paths and order. A line moved from a root instruction file into a skill therefore keeps its age, and so does a renamed file. Each copy of a line is followed separately and remembers the revision it first appeared at: when a revision has more copies of a line than before, the extra copies are new; when it has fewer, the newest copies go first, whichever file they left, so the text said to survive is the oldest. A reworded, rewrapped, or split line is a removal and an addition. A line that disappears and later comes back, as in a revert, is new again: survival means continuous presence, like `git blame`. This follows the inventory, so a file that is in it only because a Claude import reaches it loses its text's age when the import is dropped, even for one revision, although the file itself never changed. Matching is not semantic, so a short line such as `---` or a code fence can match a copy in another file by coincidence.

Lines are weighed by their trimmed stored bytes, the UTF-8 bytes for ordinary text, so a long instruction counts more than a short one and the result is the same whichever token measurement the report uses. Lines are split at the newline byte and matched by their bytes, so a file that is not valid UTF-8 keeps its distinct lines distinct; a UTF-16 file is still split at each newline byte, so its lines match only other UTF-16 copies. Bytes are not tokens: the figures are shares and byte counts, never added to `estimatedTokens`. The baseline is the first analyzed revision, so in a shallow clone the oldest cohort holds everything before the clone starts. When `shallow` is true and the first revision added instruction text, the HTML report labels the period holding it "or earlier"; when the median is that first revision, the HTML and the command line both give its date as "or earlier"; and when the first revision with instruction text is the first revision, both say the clone starts there.

A revision that added or removed lines carries `lineAge`: `added`, the bytes of copies new at that revision, and `removed`, the bytes it removed grouped by `from`, the index in `revisions` of the revision they had appeared at, oldest first. Bytes only ever leave a cohort after the revision that added them, so replaying `lineAge` in order gives each revision's text by origin; `instructionAges` in `src/instruction-age.ts` does this and the HTML report embeds it. At a target revision, the bytes whose origin is at or before a baseline revision are exactly the baseline's text that stayed present the whole time, which gives survival between any two revisions without storing it. A revision without `lineAge` moved no line, even if it changed, renamed, or added files. No line text or hash is stored, and `lineAgeMethod` (`exact-trimmed-line-multiset-stored-bytes-v1`) names the method. The byte counts can still tell a reader the length of an edited line, and that text was moved or copied between files rather than written anew, including in a shareable report.

The HTML report draws the age of the text as a stacked bar per charted revision in a collapsed **Instruction age** panel: one layer per period, oldest at the bottom and darkest in light mode (lightest in dark mode), with the period chosen as the finest of week (from Monday), month, quarter, or year that gives at most eight layers; a history spanning more than eight years keeps one layer per year. Periods follow the author date as written, the date the report shows, so after a rebase an older-looking layer can hold text added at a later revision. The chart's first and last dates sit under it, as under the history chart, and the matching rules sit behind a disclosure, as the token counting method does. Every layer keeps at least 3:1 contrast with the panel. Its legend gives the share of each period present at the selected revision, and its heading the date by which half of the text was in place and the share of the first instructional revision's text still there, naming that revision's date; in a provider tab it adds "all files". "Compare revisions" adds the share of the baseline's instruction text still present at the target, labeled "(all files)" in a provider tab. The command line prints the same two figures for the last revision. Shares are whole percentages that never round a part to 0% or 100%. `instructionAges` keeps one replay position and the HTML asks for revisions in order, so drawing the panel takes one pass over the history whatever its length. `strata diff` compares two trees without their history, so it has no instruction age, and the static SVG image does not draw it.

## Revision comparison

The offline HTML report compares any two revisions present in the report; comparison semantics are unchanged by schema versions 9 and 10; version 13 adds listed skill tokens beside the stored-text change. The timeline and target selector refer to the same revision; the baseline selector starts on "Previous revision", which follows the target so the comparison lists what the selected revision changed, and stays fixed once a specific revision is chosen. Before the first revision the baseline is empty. There is no separate list of changes at the selected revision; like any comparison, this one shows a rename as a removal plus an addition and says so, while the treemap's detail line still names a rename. The chart is capped at 100 bars, grouping adjacent revisions when needed and displaying the last revision in each group. Each bar's tooltip and accessible name give the revision numbers it covers. The chart starts at the first revision that has a tracked file in the current view, and the date under its left edge is that revision's; otherwise a repository that adopted agent configuration late would spend most of its bars on nothing. The slider covers the charted revisions so it stays aligned with the bars, and the baseline and target selectors still address every revision. While the slider is dragged, the summary, chart selection, legend, and treemap follow it immediately; the file inventory and comparison tables, which can hold thousands of rows, are redrawn once the slider settles or is released. Panels are not redrawn when moving between revisions that share the same inventory. The comparison shows signed differences in estimated stored-text tokens and tracked file counts, grouped by provider and category; groups with no difference are left out. No token percentage is shown: it is derivable from the two totals and meaningless against a zero-token baseline. Version 19 adds one share, "Instruction text kept": the share of the baseline's instruction bytes still present at the target, always over all files (see [Instruction age](#instruction-age)); it is hidden when the baseline has no instruction text or is not before the target, and a fixed baseline is marked on the instruction age chart as on the history chart. The timeline legend gives each category's stored-text tokens at the selected revision, or its file count when the category is source-only. A source-only category's swatch is hollow, since nothing is drawn in its color, and selecting the entry opens the file list filtered to that category. There is no separate composition table.

The HTML view defaults to all tracked files, counted once. A provider view includes that provider's files and the shared files it reads, by `readers`, with the Gemini view including `AGENTS.md` and `GEMINI.md` only as each revision's `geminiContextFiles` (or its default) allows, and the Cursor and Copilot views each including other tools' files only at revisions that track that tool's configuration; a shared-only view displays every shared file by itself. A provider that only appears as a reader, such as Codex in a repository whose only Codex files are under `.agents/skills`, still gets a view. Shared files can occur in several provider views, so provider totals cannot be summed to recover the all-files total. When a settings change brings a context file into or out of the Gemini view, or the first Cursor or Copilot file is added or the last removed, bringing the other tools' files that tool reads into or out of its view, that view lists them as added or removed at that revision, and its comparisons do the same, although the files themselves did not change. Switching views projects every report panel from the same stored JSON data and resets inventory filters. A move between providers appears as a removal in one view and an addition in the other. This is a display choice, not a claim about an agent's active or loaded context. The per-component change table omits file-count deltas because a single matched path can only be added (+1), removed (-1), or edited (0); aggregate file deltas remain in the provider/category and summary comparisons.

Components are matched by provider, category, and path. A changed blob at the same identity is shown as edited even if its token estimate is unchanged. A renamed or reorganized file may appear as a removal and addition; the comparison does not assert that instructions survived or that a refactor occurred. Source-only files affect file counts but contribute zero to estimated-token deltas.

## Composition treemap

The HTML report uses component measurements to draw a category-grouped treemap at the selected revision. Each positive-token instructional component receives a rectangle with area proportional to its estimated stored-text tokens; categories are contiguous and color-coded. Interior labels use the skill directory name or file name. They are checked against their rendered space and again on resize: names break only at hyphens, never mid-word; the token count is removed when both lines do not fit, then the name is reduced, then cut to one small line ending in an ellipsis, and removed only when even that cannot fit. Each category is a block in a darker shade of its color, cut off from its neighbors by a gap; a block large enough to spare a band names its category and stored-text tokens there, and smaller blocks rely on the timeline legend above, which uses the same colors. Thin seams of that shade separate the files inside a block. The treemap is laid out at its drawn size in pixels, so gaps and bands keep their size on any screen, and it is laid out again when resized. A category's block, band included, has an area proportional to its tokens apart from the gaps; the files inside share what is left in proportion to each other. Layout aims for rectangles about twice as wide as tall, so a file name fits on one line where a square would break it. When the selected revision changes, each rectangle moves from its old place to its new one, and a file new to the view fades in; this is skipped when the system asks for reduced motion. Every rectangle has a hover/focus detail line and an accessible name with the full path and token count; there is no separate browser tooltip repeating it. A rectangle whose file the selected revision added is outlined with a solid line, and one it edited or renamed with a dashed line; the detail line and accessible name say the same in words. The outline describes that one commit against its first parent, like the list of changes at this revision, and files a commit removed have no rectangle to mark. Source-only and zero-token components have no area and remain in the inventory; their counts, with the categories of the source-only files, are on the line under the treemap, which gives way to a rectangle's details while it is hovered or focused. A tall, narrow rectangle sets its name top to bottom rather than breaking it mid-word. The treemap is a stored-configuration composition view, not a map of runtime dependencies or loaded context. Keyboard-accessible rectangles locate the corresponding inventory row; the table remains the text alternative. The skill-bundle list is collapsed under its heading, which gives the bundle count, and is left out when the revision has no skill bundles; opened, it begins with eight rows and offers an explicit control to reveal the rest.

Rectangle layout uses `d3-hierarchy@3.1.2`'s squarified treemap. The generated report embeds the minified library and its ISC license and calculates the selected revision's layout in the browser; it requires no network access or separate assets.

## Report masthead

The HTML report's masthead names the analyzed repository and holds the figures for the selected revision. Its lower edge repeats the timeline as stepped category layers, following the same view, grouping, and scale as the chart beneath it; the layers use the chart's category colors and are decoration, hidden from assistive technology. The headline face, Archivo under the SIL Open Font License, and the page icon are inlined as `data:` URLs. The content security policy therefore allows fonts and images from `data:` only; the report still loads nothing from the network. The Strata name in the masthead and footer links to the package's npm page; it is the report's only outbound link, is followed only on click, opens without a referrer, and is the same in every report, so it carries nothing about the analyzed repository. [docs/brand](brand/README.md) describes the logo, colors, and type.

Category colors are shared by the HTML report and the SVG image. Instructions and skills take the brand's verdigris and clay hues and the other categories are spaced around them; the set is checked so that categories adjacent in the stack stay distinguishable under protanopia and deuteranopia and keep at least 3:1 contrast on both the light and the dark page ground. Treemap labels are white or near-black, whichever contrasts more with the category color, or with its shade for a category band. Token and file changes are colored by direction only, ochre for growth and verdigris for reduction, in darker steps on the light ground: stored configuration growing is not a failure, so the report does not use red and green, and the sign always carries the direction. The report follows the system's light or dark setting; the masthead is the same in both.

The tracked-components table is collapsed under its heading, which gives the file count; selecting a treemap rectangle opens it. With `--precise` or `--provider-api` it starts open, because the per-provider counts appear only there. It and the changed-components list show their first 25 rows, each with a control to show the rest. This limits what is drawn, not what is counted: totals, filters, and comparisons always cover every file. The measurement method and its limits sit behind a disclosure whose visible label states that the figures describe what Git stores, not loaded session context; a shallow-clone warning and a warning naming submodules that were not analyzed stay visible outside it. With provider counts, that label also names each provider's method in one word: `API count` for `api-counted` (Anthropic documents its count endpoint as an estimate, so the report does not call it exact), `exact (local)` for `encoding-exact`, or `estimate`. Opened, it shows one row per provider with the model, where the text was counted, and the credential source, or why the estimate was used; the full method is in the row's tooltip, and the selected view's provider is bold. The notice that a shareable report replaced names and paths stays visible outside the disclosure.

## SVG image

`strata analyze --format svg` writes a static image of the history for a README or similar page. It draws the all-files view from the stored revision totals, so it needs no inventory replay. Each category with stored-text tokens is a stepped layer stacked on the previous ones in category order, using the HTML report's colors. The layers carry no outline: the top edge of the stack is the total. The chart follows the HTML timeline's rules: it starts at the first revision with a tracked file, holds at most 100 steps, and each step shows the last revision in its group. As in the HTML timeline, the vertical scale and legend cover every charted revision, so a peak or category inside a group is not dropped from them. Notes state when revisions were grouped and how many leading revisions without tracked configuration were left out. Axis steps are whole numbers. A header gives the latest token total, tracked-file count, revision count, and the token change since the first charted revision. The measurement label and a statement that this is stored configuration, not loaded session context or billing, are part of the image, as is a shallow-clone warning when it applies.

The image contains the repository and branch names, the first and last charted dates, category labels, and totals. It contains no paths, commit IDs, blob IDs, source text, script, links, or external resources, so it displays wherever SVG images are allowed, including GitHub READMEs. `--shareable` replaces the repository and branch names. Repository-derived text is XML-escaped, and characters XML cannot carry are removed. Text width is not measured, so the repository label is truncated to 60 characters and legend entries are placed by an estimated width. The output is deterministic for a given report: it contains no generation time. Because the image is meant for publication, the CLI does not restrict it to mode `0600` as it does HTML and JSON reports: a new image gets the permissions the user's umask allows, and an existing file keeps its mode.

## Badge

`strata analyze --format badge` writes a small JSON file in the [shields.io endpoint schema](https://shields.io/badges/endpoint-badge) (`schemaVersion: 1`), so a README can show the latest stored-text total as a badge through `https://img.shields.io/endpoint?url=<published file>`. The label is `agent context` and the message is the latest revision's token total, prefixed with `≈` unless the measurement is encoding-exact, so an estimate is never shown as an exact count. The colors are the Strata palette; shields' own query parameters can override the label, colors, and style without a Strata option. The file holds the number and its kind only: no repository or branch name, path, commit ID, date, or source text, so `--shareable` does not change it. Like the image, it is meant for publication and is written with ordinary file permissions. The badge is a stored-configuration figure like every other Strata total, not loaded context or billing; the surrounding README should say so where it matters.

`--minimal` reduces the image to the layers alone, for a banner or decorative use. It is 800 by 200 with a transparent background, and the layers fill it edge to edge: the tallest charted revision touches the top, so heights are relative and there is no axis to read a value from. It has no visible text, grid, legend, or notes, and so shows neither the measurement label nor the stored-configuration statement, nor the grouping, late-start, and shallow-clone notes; use the full image where a reader needs to interpret the numbers. The bucketing, chart start, category order, and colors match the full image. Its accessible description names the measurement kind and the latest totals. It contains no repository or branch name and no dates, so `--shareable` does not change it. `--minimal` with another format is a usage error.

## Pull-request comparison

`strata diff` compares two supplied full commit IDs by reading their tracked Git trees directly. It does not check out revisions or write into the target repository. It uses the same path classification, instructional-text boundary, and selected measurement mode as the history report. Its JSON has a separate schema version 11, whose compared components carry the report's provider labels (so `.agents/skills` files are `shared`); it has no provider views. Version 6 adds the comparison's `skillListing` totals, with the manifests at each side and the unresolved ones the totals leave out, and a `listing` on each changed skill manifest, measured as in [Skill listings](#skill-listings); the Markdown adds a listed-token line when either commit has a skill manifest and a `Δ listed` column when a manifest changed. Version 7 recognizes Cursor files, so compared components and `byProvider` can carry `cursor`, and a changed `.cursorrules` carries `legacy: true`; the same two commits can give larger totals than under version 6. Version 8 recognizes Copilot files in the same way, with `copilot` and `legacy: true` on a changed `.chatmode.md`. Version 9 resolves Claude `@path` imports in each tree, so files they reach are compared too and carry `imported: true`, and the Markdown file table adds "(imported)" to their change; totals can be larger than under version 8. Version 10 adds `upFront`: for each provider that reads stored text at either commit, its [up-front and on-demand totals](#up-front-context) at both, with the file count and unresolved counts; the Markdown adds a table of the providers whose figures changed, or a line saying none did. Version 11 adds `mcp` when either commit has a component with an [MCP server list](#mcp-servers): the servers at both, the files whose servers could not be read, and the servers `added` and `removed`, each with its name, path, and provider; the Markdown adds a line naming up to ten of each. With `--precise` it adds `providerMeasurements` and `providerTotals`, resolving each commit's Gemini settings to decide which context files Gemini reads; Markdown is intended for a local file or an opt-in GitHub Actions job summary. Paths and commit IDs are visible, but source text is not. The composite Action does not post comments or enforce a token budget.
