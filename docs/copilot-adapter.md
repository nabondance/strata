# GitHub Copilot repository configuration

Implemented in report schema version 15; [the analysis scope](analysis-scope.md) lists the patterns as recognized. This page keeps the evidence behind them. Studied 2026-10-17; open questions checked 2026-10-18 against VS Code 1.142.0 source, the Copilot CLI 1.0.98 changelog, and the GitHub Docs source. GitHub Copilot is several clients, not one agent: Copilot Chat on GitHub.com, the cloud agent (formerly the coding agent), code review, Copilot CLI, and Copilot Chat in VS Code, Visual Studio, JetBrains, Eclipse, and Xcode. Each reads a different subset of the same tracked files; GitHub's [support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support) is the authority for which surface reads which instruction type. The adapter adds provider `copilot`. A Copilot label means "documented as read by at least one Copilot surface", never that a given session loaded the file.

Copilot also reads files that Strata already assigns to other providers: `AGENTS.md`, `CLAUDE.md`, `REVIEW.md`, `GEMINI.md`, `.claude/agents`, `.claude/rules`, `.claude/skills`, `.agents/skills`, and `.mcp.json`. Those stay one component each, counted once, as `AGENTS.md` already is for Cursor.

## Copilot-owned paths

| Tracked path | Proposed classification | Evidence and boundary |
| --- | --- | --- |
| `**/.github/copilot-instructions.md` | Copilot / instructions / stored instructional text | [Repository instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions): one repository-wide file in the root `.github` directory, no frontmatter, applied to every request in the repository. Every surface in the matrix reads it except Eclipse code review. GitHub.com reads the root file; [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions) also reads it in the working directory and the directories between it and the root, so a nested project's file is recognized too. |
| `**/.github/instructions/**/*.instructions.md` | Copilot / rules / stored instructional text | Same page: any depth under `.github/instructions`, name must end in `.instructions.md`. Frontmatter `applyTo` takes comma-separated globs relative to the repository root (`*` one directory, `**` any depth); `excludeAgent: "code-review"` or `"cloud-agent"` hides a file from that surface. GitHub.com Chat does not read these files. [VS Code](https://code.visualstudio.com/docs/copilot/customization/custom-instructions) also loads one on demand when its `description` matches the task, and only manually when it has neither `description` nor `applyTo`. VS Code [searches subfolders up to five levels deep](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts); deeper files are still recognized, since the CLI documents no limit. These are conditional, like Claude rules, so the category is `rules`, not `instructions`. Do not interpret `applyTo` or `excludeAgent`. Other `.md` files there are ignored by Copilot and should be `other`, source only. |
| `**/.github/prompts/*.prompt.md` | Copilot / commands / stored instructional text | [VS Code prompt files](https://code.visualstudio.com/docs/copilot/customization/prompt-files): Markdown with `.prompt.md`, invoked manually with `/name`, the Command Palette, or the editor play button; "supported only in Local harness sessions". Their size is not an always-loaded cost. VS Code [reads only files directly in the folder](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts); its subfolder search applies to instruction files alone, so recognize direct children only. Copilot CLI and GitHub.com do not document prompt files. |
| `**/.github/agents/**/*.md`, except `README.md` | Copilot / agents / stored instructional text | [Cloud agent custom agents](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/create-custom-agents) live in `.github/agents` and use `.agent.md`; the [configuration reference](https://docs.github.com/en/copilot/reference/custom-agents-configuration) names agents from the file name "minus `.md` or `.agent.md`", requires `description`, lets `target` (`vscode` or `github-copilot`) restrict the surface, and limits the prompt body to 30,000 characters. VS Code [treats any `.md` file directly in `.github/agents` as an agent, except `README.md`](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts), and does not search its subfolders. Copilot CLI [discovers agents recursively in subdirectories (1.0.55) and in nested `.github/agents` directories between the working directory and the repository root (1.0.62)](https://github.com/github/copilot-cli/blob/main/changelog.md). The pattern is the union. GitHub.com's cloud agent does not document subfolders, which the label allows. `README.md` stays source-only `other`, because VS Code skips it and the CLI's handling is undocumented. Frontmatter (`tools`, `model`, `mcp-servers`, `handoffs`, `hooks`) is stored text and not interpreted. |
| `.chatmode.md` files | inside `.github/agents`: Copilot / agents, `legacy: true`; in `.github/chatmodes`: source-only `other` | Custom agents "were previously known as custom chat modes". VS Code still [parses `.chatmode.md` as an agent file](https://github.com/microsoft/vscode/blob/1.142.0/src/vs/workbench/contrib/chat/common/promptSyntax/config/promptFileLocations.ts), but its default agent folders are `.github/agents` and `.claude/agents` only. The deprecated `chat.modeFilesLocations` setting still declares `.github/chatmodes` as its default, but the file locator no longer reads that setting, and VS Code offers to migrate those files. So a `.chatmode.md` in `.github/agents` is still read and is labeled legacy, as `.cursorrules` is; one left in `.github/chatmodes` is read only when a user adds that folder to `chat.agentFilesLocations`, a setting outside the repository. Keep it visible as source-only `other`. |
| `.github/skills/<name>/SKILL.md` | Copilot / skills / stored instructional text, plus listing | [Copilot skills](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/add-skills): one directory per skill, a `SKILL.md` with required `name` and `description` frontmatter, used by the cloud agent, code review, CLI, and VS Code and JetBrains agent mode. Copilot picks a skill "based on your prompt and the skill's description" and then injects `SKILL.md`, so the existing listing measurement applies. |
| Other files under `.github/skills/<name>/` | Copilot / skills / source bytes only | Same page: Copilot "automatically discovers all of the files in the skill's directory". Same rule as other skill resources. Copilot CLI also [discovers skills recursively and supports namespaced skills](https://github.com/github/copilot-cli/blob/main/changelog.md), so `.github/skills/<group>/<name>/SKILL.md` can be a skill; check that the existing skill-root rule groups such a bundle by its manifest's directory, not by `<group>`. |
| `**/REVIEW.md` | Claude / instructions, with Copilot as a conditional reader | [Copilot code review](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review) "also reads custom instructions from `CLAUDE.md`, `GEMINI.md`, and `REVIEW.md` files in your repository", from the pull request's head branch; the [changelog that added it](https://github.blog/changelog/2026-07-17-copilot-code-review-customization-and-configurability-improvements/) frames them as files teams "already maintain" for other tools. [Claude Code's Code Review](https://code.claude.com/docs/en/code-review-customize) owns the convention: a root file, plus subfolder files that add checks for changes under them, read from the base or default branch. So `REVIEW.md` is labeled Claude at any depth, with `readers` `["claude", "copilot"]`, and on its own does not mark a repository as using Copilot. |
| `.github/hooks/*.json` at the root | Copilot / settings / source bytes only | [Hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference): JSON with `version: 1` and a `hooks` object, loaded by the cloud agent and CLI. Commands are not prompt text. Strata has no `hooks` category; Claude hooks also count as `settings`, so keep that. |
| `.github/copilot/settings.json`, `.github/copilot/settings.local.json` | Copilot / settings / source bytes only | Same page: Copilot CLI reads inline `hooks` and `disableAllHooks` there; the cloud agent does not. The local file is usually ignored, so it is rarely tracked. |
| `**/.github/mcp.json` | Copilot / tools / source bytes only | [CLI MCP servers](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers): shared, committed project configuration. The CLI loads project servers only after folder trust, from every directory between the working directory and the root. |
| `.vscode/mcp.json` | Copilot / tools / source bytes only | [VS Code MCP servers](https://code.visualstudio.com/docs/copilot/customization/mcp-servers): workspace config with a top-level `servers` object. Copilot CLI does not read it. Other `.vscode/` files are editor settings; do not recognize them. |
| `.github/workflows/copilot-setup-steps.yml` | Copilot / settings / source bytes only | [Cloud agent environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/customize-the-agent-environment): a workflow with a single `copilot-setup-steps` job, run before the agent starts, only from the default branch. It configures the agent's environment, not its prompt. Other workflows stay unrecognized. |
| `.github/workflows/copilot-code-review.yml` | Copilot / settings / source bytes only | [Code review environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review#customizing-copilot-code-reviews-environment): when present, code review uses it "instead of `copilot-setup-steps.yml`", which it otherwise reuses. Added in the [2026-07-17 changelog](https://github.blog/changelog/2026-07-17-copilot-code-review-customization-and-configurability-improvements/). |

## Decision: Copilot is a conditional reader, like Cursor

Copilot documents reading files labeled `claude` or `gemini`. Relabeling them `shared` would move tokens out of the Claude and Gemini CLI totals in every repository, and leaving them out would make the Copilot view miss the instructions many repositories give it. The Cursor adapter had already met this with `.claude/skills`: the owner keeps its label, the file lists the other tool in `readers`, and that tool reads it only at a revision that tracks its own configuration. Copilot needs no repository file either, so it uses the same rule, separately from Cursor: `providerReads` counts a borrowed file for Copilot only at a revision with at least one `copilot` component, and a history without one drops `copilot` from every `readers`. A repository that does not track Copilot files is reported exactly as before. The cost is the same as for Cursor: a team using Copilot with only `AGENTS.md` or `CLAUDE.md` is not detected.

## Boundaries

- Label no surface. Which client read which file (Chat, cloud agent, code review, CLI, IDE) depends on the user, not the repository, so the report must not say "code review read this".
- Do not interpret `applyTo`, `excludeAgent`, `target`, `description`, or `.claude/rules` `paths`. They are stored text; whether they matched a session's files is runtime evidence.
- Do not resolve precedence: nearest `AGENTS.md`, the `CLAUDE.md`/`GEMINI.md` alternative, `.mcp.json` over `.github/mcp.json`, or repository-level agents overriding organization-level ones.
- Organization and enterprise configuration (`agents/*.agent.md` in a `.github` or `.github-private` repository), personal instructions, `~/.copilot/`, and settings stored in GitHub (code review's "Use custom instructions" toggle, cloud agent MCP configuration in repository settings) are outside the repository and out of scope.
- `@path` references in `copilot-instructions.md`, `AGENTS.md`, and `CLAUDE.md` are expanded by the CLI but not in `GEMINI.md` or `*.instructions.md`. Do not add their contents or draw edges without resolving them.
- GitHub sets no size limit for instruction files. Code review used to stop reading `copilot-instructions.md` and `*.instructions.md` at 4,000 characters; [that limit was removed on 2026-06-12](https://github.blog/changelog/2026-06-12-copilot-code-review-new-configurations-and-controls/). Do not truncate; a report of an older revision measures the stored file, not what code review read at the time.
- There is no Copilot token count endpoint. Copilot files keep the report's measurement under `--precise`, as Cursor's do.

## Coverage

The synthetic history in `test/analyze.test.mjs` starts with Claude, Codex, and Gemini CLI files and ordinary `.github` files (a CI workflow, an issue template, a pull request template) and asserts that the report never mentions Copilot. It then adds root and nested `copilot-instructions.md`; a nested `.instructions.md` with `applyTo` and a `README.md` beside it; a prompt file and one in a subfolder (source-only); an `.agent.md`, a plain `.md` agent in a subfolder, an agents `README.md`, a `.chatmode.md` in `.github/agents` (legacy) and another in `.github/chatmodes` (source-only); a skill with a resource, an unlistable skill, a loose `SKILL.md`, and a namespaced skill; `REVIEW.md` at the root and in `docs/` (Claude, read by Copilot); a `.claude/rules/README.md` (no Copilot reader); a Cursor rule that outlives the Copilot files; hooks, CLI settings, both MCP files, and both environment workflows; then migrates the chat mode by rename and removes Copilot. It checks the readers, the per-revision Copilot view in Node and in the HTML report, listings, `strata diff`, shareable redaction, and that `--precise` sends no Copilot text. `test/provider-view.test.mjs` checks that Copilot's and Cursor's conditions are independent.

Copilot CLI's namespaced skills (`.github/skills/<group>/<name>/SKILL.md`) are grouped under `<group>` as source-only resources and not listed, because a path rule cannot see whether a sibling manifest exists. Supporting them needs a skill root chosen from the manifests present at each revision.
